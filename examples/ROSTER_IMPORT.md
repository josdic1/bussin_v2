# Load the roster before testing

This is a local prelaunch import for rider and guardian contact records. It does not invite guardians or grant access. Keep real roster files outside the repository; they contain children's personal information. The included example contains only invented identities.

1. Use one PostgreSQL database per organization. The existing `bussin_v2` database contains local test records. Back it up, run `npm run db:migrate -w @bussin/server`, then `npm run tenant:init -w @bussin/server -- local-test "Local test"`. Add `BUSSIN_TENANT=local-test` to `server/.env`. The server refuses to start if its configured key differs from the database identity. Migrations 009 and 010 preserve existing riders and move all guardian records into one contacts table.
2. Copy `examples/roster.example.json` to a private location, then replace the invented rider and guardian records with your roster. `dataset` must equal the claimed tenant key for **this database**. Each rider and guardian needs a stable unique `key` from the source system. Never use a name, address, or row number as an identity key. If the JCC sheet does not include stable IDs, ask for those before importing real children.
3. For each rider, provide `givenName`, `familyName`, and one or more guardians. Contact `email` and `phone` may be `null`. `am` and `pm` may be `null` until routes are confirmed. When assigned, `route` and `stop` must match the saved route name and saved stop label exactly. A school arrival stop is usually not a child's AM pickup; a school departure stop is usually not a child's PM drop-off.
4. Run `npm run roster:import -w @bussin/server -- preview /absolute/path/roster.json` and review the counts and stop mapping. If correct, run the same command with `apply`. Run `npm run dev` to view the roster. Reimporting with the same dataset and keys updates records; missing existing rider keys fail validation rather than deleting children.

The example assumes the Alpha routes from the local test database. Edit its route and stop labels or set `am`/`pm` to `null` if those routes are absent. Imported guardian contacts are separate from login accounts; a phone number or email in an operational spreadsheet does not mean the person signed up or consented to alerts. Existing manual test riders remain visible. The Guardians tab lists every contact, including unlinked contacts, and lets an admin add one and link it to a rider. Reimport replaces imported contact details, but manual links survive. Never point a JCC deployment at the local test database: initialize a separate empty database, claim it as `jcc`, and create its accounts and routes there. Spreadsheet-to-JSON conversion is still needed for the JCC sheet.
